# Prospective vs Retroactive mode

Every spec generated by this skill is written in one of two modes. Ask the user which one applies
before generating anything (see `gathering_questions.md`) — the two modes fill the same three
files very differently.

## Prospective — spec written before the feature is built

Use when: the feature doesn't exist in code yet; the spec is meant to be handed to `il-screen-builder`
(or a human developer) as a work order.

- `requirements.md`: acceptance criteria describe the *intended* behavior. "Open questions" starts
  empty or with genuinely open design questions — there is no implementation to consult for
  answers.
- `design.md`: describes the *planned* architecture — which layers will exist, which API calls are
  expected. Any API without a confirmed contract is explicitly called out as
  "planned, contract not yet confirmed", not written as if it already exists.
- `tasks.md`: every single item starts unchecked (`[ ]`). There is nothing to mark done yet.
- `changelog.md`: starts at `v1.0 (initial)`.

## Retroactive — spec written from an already-implemented feature

Use when: the feature already exists in the codebase (fully or partially) and the user wants the
spec to document it accurately — e.g. onboarding a new AI/human contributor, or catching up on
documentation debt. This is how `Docs/Specs/SignUp/` was created.

- **Before writing `requirements.md`/`design.md`, read the actual code**:
  `InnerLamp/Presentation/Scenes/<Feature>/`, `InnerLamp/Domain/Entities/`,
  `InnerLamp/Domain/UseCases/<Feature>/`, `InnerLamp/App/DIContainer.swift` wiring, and any
  existing `README.md` under the feature's scene folder.
- `requirements.md`: acceptance criteria describe what the shipped behavior *actually* does —
  don't describe an idealized version that doesn't match the code. If the code has a stub (e.g. no
  real network call), say so plainly in a "Pending" section, not folded into "done" criteria.
- `design.md`: the Layers & components table must name the actual files that exist, not
  hypothetical ones. Any stubbed method (e.g. a UseCase method that's a one-line `print("TODO")`)
  gets its own "Deliberately stubbed for now" note explaining what's missing and why (per the
  project's "never fake a Repository call" rule — see `il-screen-builder`'s
  `references/data_layer_boundaries.md`).
- `tasks.md`: mark `[x]` only for what you actually verified exists and works in the code; mark
  `[ ]` for anything missing, stubbed, or partially done. Don't trust a prior README's claims
  without spot-checking — retroactive specs exist specifically to correct documentation drift, not
  reproduce it.
- `changelog.md`: still starts at `v1.0 (initial)`, but its entry should say "written retroactively
  from the existing implementation" (see `Docs/Specs/SignUp/changelog.md` v1.0 for the exact
  wording pattern to reuse).

## Mixed case: feature partially built

Common in practice — some phases done, others not. Treat it as Retroactive for the done parts and
Prospective for the rest, in the same three files (this is exactly what `Docs/Specs/SignUp/` does:
Phase 1–2 retroactive/done, Phase 3 prospective/pending). Don't split into two separate spec sets.
